A cache-through layer is a piece of glue that sits between a service and its slow backing store: on a read, it checks the cache first, and only falls through to the database on a miss. Writes update both. Before this fictional PR, the endpoint read straight from the DB every time, with no cache at all — fine at 10 QPS, not fine at 10K QPS.

Reads now check Redis before the database. Cache keys carry a schema version so two deploys can share one Redis without a cutover stampede. If Redis is unreachable the middleware serves from a bounded in-memory LRU instead of raising — the cache is an optimization, never a source of truth.

Three concerns are wired together above: a Redis client for the primary cache, an in-memory LRU for the fallback path when Redis is down, and a small resolver that keeps them consistent. The sequence above shows the read path; write paths (not diagrammed) always populate Redis first, then LRU.

class CacheThroughMiddleware:
    def __init__(self, redis: Redis, lru: LRUCache, schema_version: str) -> None:
        self.redis = redis
        self.lru = lru
        self.schema_version = schema_version

    async def get(self, widget_id: str) -> Widget | None:
        key = f"widget:{widget_id}:{self.schema_version}"
        try:
            raw = await self.redis.get(key)
        except RedisConnectionError:
            return self.lru.get(key)
        if raw is None:
            return None
        try:
            return Widget.model_validate_json(raw)
        except ValidationError:
            # Corrupt payload: treat as miss and evict aggressively.
            await self.redis.delete(key)
            return None

The schema_version suffix in the key format is doing real work: it lets old and new schema versions coexist during a rolling deploy without a cache-warming stampede at cutover.
