Uma camada cache-through é a cola entre um serviço e seu store de trás lento: numa leitura, checa o cache primeiro, e só cai pro banco em miss. Writes atualizam os dois. Antes deste PR fictício, o endpoint lia direto do banco toda vez, sem cache nenhum — tudo bem a 10 QPS, não tudo bem a 10K QPS.

Agora as leituras checam o Redis antes do banco. As chaves de cache carregam uma versão de schema pra dois deploys poderem compartilhar um Redis sem stampede de cutover. Se o Redis está inalcançável, o middleware serve de um LRU em memória limitado em vez de levantar — o cache é uma otimização, nunca fonte de verdade.

Três preocupações estão amarradas acima: um cliente Redis pro cache primário, um LRU em memória pro caminho de fallback quando o Redis está fora, e um pequeno resolver que os mantém consistentes. A sequência acima mostra o caminho de leitura; caminhos de write (não diagramados) sempre populam o Redis primeiro, depois o LRU.

class CacheThroughMiddleware:
    def __init__(self, redis: Redis, lru: LRUCache, schema_version: str) -> None:
        self.redis = redis
        self.lru = lru
        self.schema_version = schema_version

    async def get(self, widget_id: str) -> Widget | None:
        key = f"widget:{widget_id}:{self.schema_version}"
        try:
            raw = await self.redis.get(key)
        except RedisConnectionError:
            return self.lru.get(key)
        if raw is None:
            return None
        try:
            return Widget.model_validate_json(raw)
        except ValidationError:
            # Payload corrompido: trata como miss e evita agressivamente.
            await self.redis.delete(key)
            return None

O sufixo schema_version no formato da chave está fazendo trabalho de verdade: deixa versões de schema antiga e nova coexistirem durante um rolling deploy sem stampede de aquecimento no cutover.
